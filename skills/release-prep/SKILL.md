# release-prep

這是一份**發版整備清單**，把「版本號 → 文件 → 基準 → 掃描 → 提交與推送 →
標籤 → CI → Release 驗證 → 紀錄」固定成可重複套用的順序，讓每次發版的漏項
能被同一份清單擋下來。

- 它是清單與流程，不是發版腳本；不會自動 bump 版本、commit、push 或建立 Release。
- 它不保證掃描通過就等於安全；掃描結果只代表「這次掃了什麼、退出碼是什麼」。
- 載入它**不等於授權**任何提交、推送、標籤或發佈動作；每一項都要有明確授權。

## 什麼時候用

- 使用者核准發版後、打標籤之前。
- 需要補驗既有 Release 頁面（摘要亂碼、附件數量、授權資料）時。
- 需要把「這次發版做了什麼、掃描裁定是什麼」寫成可追溯紀錄時。

## 前置：授權與狀態

1. 取得並分開確認四種授權：**提交**、**推送主線**、**推送標籤**、**建立或修改
   Release**。使用者核准「發版」不自動等於核准其中任何一項，除非他明確說了。
2. 確認版本號：舊版 → 新版，以及語意（主版／次版／修補）由誰決定。
   沒有明確指定就問，不要自行挑一個。
3. 確認工作樹與遠端狀態：本地是否有未提交或不相關的變更、分支是否落後遠端。
   有疑慮先停下來回報，不要自動 stash、reset 或 rebase。
4. 確認這次要同步的文件清單與 CI 的必要 job 清單（沒有就建立一份，之後每版沿用）。

## 步驟

1. **版本號 bump（同源檢查）**
   - 先列出所有存放版本號的位置：各服務、桌面端、CLI、套件 manifest、lockfile、
     版本常數、建置設定、文件狀態行。用一次搜尋把舊版號的所有出現位置找出來。
   - 逐一更新，**不要只改一處**；更新後再搜尋一次舊版號，確認沒有殘留
     （歷史紀錄與 changelog 的舊版號屬於刻意保留，要在紀錄裡註明）。
   - 多個子套件共用同一版號時，確認它們真的同源；若刻意不同版，寫下理由。
   - 文件狀態行只放「本版重點一句」，不是 changelog 全文。
2. **文件同步**
   - 依本版內容清單逐項確認：行為契約、環境變數與設定表、安裝與升級步驟、
     必要的使用說明段落。
   - 驗證方式是「文件描述的行為與程式現況一致」，不是「檔案有改過」。
   - 契約變更要寫明破壞性與升級注意；沒變更的段落不要順手重寫。
3. **本地基準全綠**
   - 逐套件跑測試與建置（不是只跑根目錄一個指令），記下每個套件的通過數與失敗數。
   - 與上一版的基準比對：**只增不減**；新增的失敗要先查清楚是本次造成還是既有。
   - 不得刪除、跳過或弱化斷言，也不得為求綠燈寫死測試輸入。
   - 既有失敗不掩蓋：在紀錄裡分開列「本版造成」與「發版前已存在」，不要宣稱全綠。
4. **提交與推送主線**
   - 提交由持有 index 權限的人執行；提交訊息說明版本與重點，不要混入無關變更。
   - 推送前跑專案既有的秘密與隱私掃描（hooks 或掃描腳本）。沒有掃描工具時，
     明確寫「未掃描」，不要當成通過。
   - **退出碼語意照抄**：0 通過、1 有發現、2 未掃完。2 不等於 0。
   - 有發現時先撤銷或輪替憑證，再處理內容；不要自動修復、不要用 `--no-verify`
     或任何等價方式繞過 hook。
   - 掃描結果翻成白話：掃了什麼範圍、退出碼、筆數、哪些是誤報與理由。
5. **標籤**
   - 用 annotated tag，訊息與版本、重點一致；標籤指向**已推送**的主線提交。
   - 標籤推送前再掃一次待推送內容。
   - 既有誤報走「誤報裁定與放行」：逐筆記規則、檔案、行號、理由，且**逐次取得
     使用者核准**；沒有核准就不放行。
6. **CI 監看**
   - 逐一確認必要 job：測試基準、各平台建置、產出物與 Release 產出。不要只看
     整體狀態一個綠燈。
   - 失敗先分辨是本次變更、環境或基礎設施問題；基礎設施問題要重跑並註明。
   - 紀錄每個 job 的結果與執行識別（可複核的連結或編號）。
7. **Release 驗證**
   - 附件：數量與名稱是否符合預期，授權與第三方聲明是否齊全。
   - **說明產生器與版本範圍**：先確認發佈說明是由哪個產生器寫出來的（CI 步驟、CLI
     或平台自動產生），以及它用什麼規則判定「上一個版本」——tag pattern 是否只認版本
     tag、會不會把快取／快照／測試用的 tag 當成上一個版本、`git describe` 的結果是否
     被非版本 tag 污染。範圍算錯，說明的變更清單就會被截斷或夾帶無關項目；**必要時
     先修 CI，再打標籤**，不要用手寫補救掩蓋產生器的缺陷。
   - 發佈說明：版本、重點、升級注意是否與實際變更一致。
   - **手動改寫要留紀錄**：任何手動編輯過的說明，都要記下「改了什麼、為什麼改、對照
     哪一次 CI 執行（run 識別）」，並寫進紀錄段；否則下一版無法判斷問題是否已根治。
   - 頁面摘要：是否乾淨（沒有控制字元、終端機轉義序列、亂碼、被吃掉的換行）。
   - 無法目視的 repo（例如 private）改用平台 API 取原文驗證，並在紀錄裡寫明
     「以 API 驗證，未目視」，不要假裝看過頁面。
   - **換 repo 後舊連結會失效**：專案換到新 repo（例如重建為公開 repo）之後，舊網址會
     404；說明與紀錄**不得引用舊連結**，一律以當下 remote 產生的連結為準，並註明驗證方式。
8. **紀錄**
   - 發版條目：版本、日期、對應提交、標籤、CI 結果、Release 驗證結果。
   - 掃描裁定：指令、範圍、退出碼、筆數、逐筆理由與核准者。
   - 已知未解項與下一版待辦；未 push 的內容要寫明「僅本機可見」。

## 發版檢查清單（逐項打勾）

| # | 項目 | 完成判準 |
| --- | --- | --- |
| 1 | 授權 | 提交、推送、標籤、Release 各自被明確核准 |
| 2 | 版本號 | 所有來源同源，舊版號無非預期殘留 |
| 3 | 文件 | 契約、設定表、升級步驟與程式現況一致 |
| 4 | 基準 | 逐套件結果已記錄，與上版比對只增不減 |
| 5 | 掃描 | 退出碼與筆數照抄，2 不當通過 |
| 6 | 提交與推送 | 主線已推送，提交內容與版本相符 |
| 7 | 標籤 | annotated、指向已推送提交、推送前已掃描 |
| 8 | CI | 每個必要 job 都確認，不是只看整體 |
| 9 | Release | 附件、說明、頁面摘要皆驗證並註明方式 |
| 10 | 紀錄 | 發版條目與掃描裁定可追溯 |

## 失敗與例外處理

- **標籤已推送才發現內容錯**：不要移動或重寫已推送的標籤（除非使用者明確授權
  並了解快取與下游影響）；優先發修補版，或在 Release 說明加註更正。
- **掃描有發現**：先停止推送，撤銷或輪替憑證，再處理；不把「已排除」當成已修復。
- **CI 只有部分綠**：把紅的 job 與原因寫進紀錄，不要用「大致通過」帶過。
- **文件來不及同步**：寧可延後發版，也不要把已知不一致的文件一起發出去。

## 輸入與輸出

- 輸入：版本號（舊 → 新）、本版內容清單、待同步文件清單、必要 CI job 清單、
  掃描與 Release 的授權範圍。
- 輸出：發版整備提交、掃描與裁定紀錄、已推送的標籤、CI 結果、Release 驗證清單、
  發版條目。

## 明確不做的事

- 不自行決定版本號語意，也不自行核准提交、推送、標籤或 Release。
- 不繞過掃描 hook，不把「掃描未完成」寫成「沒有問題」。
- 不刪除、跳過或弱化測試與斷言來換取綠燈。
- 不移動、重寫或強制推送已發佈的標籤與歷史。
- 不在 Release 說明或紀錄裡放未去識別的內部資訊、個人路徑或憑證。
- 不順手修範圍外的程式碼或重排文件；發現的問題只回報。
