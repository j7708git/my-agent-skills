# 計畫（plan）

> 使用方式：把整份檔案複製到 private notes repo 的專案目錄，命名為 `plan.md`。
> 所有 `<...>` 都要換成實際內容；不確定的欄位寫在「未知」，不要用猜測補滿。

## 骨架

```markdown
# 計畫：<專案名稱>

> **讀者**：<要執行或審查這個計畫的人；寫明熟悉程度>
> **一句話**：<這個計畫要達成什麼、怎麼算完成>
> **現在要做**：<下一個要執行的里程碑或決定>
> **依據**：<需求來源、研究筆記或任務卡>

- 專案 ID：<project-id>

## 目標

<可判定的目標>

## 背景

<為什麼要做、目前的痛點、相關的既有脈絡>

## 已知

- <已可查證的事實>

## 假設

- <可逆的預設決定>；若不成立，改為 <替代做法>

## 未知

- <還不確定、且會影響方向或風險的事>：<打算怎麼查>

## non-goals

- <明確不做的事>

## 里程碑

- <里程碑一>：<可觀察的完成定義>
- <里程碑二>：<可觀察的完成定義>

## 工作分解

- <工作項目>：<產出／負責角色>

## 依賴

- <相依對象或條件>：<影響>

## 驗收條件

- <條件>：<用什麼方法驗證>

## 風險與緩解

- <風險>：<緩解方式>

## 授權需求

- <需要明確授權的動作，例如 commit／push／安裝 hooks／改可見度>
```

## 欄位填寫規則

| 欄位 | 填寫規則 |
| --- | --- |
| 目標 | 可判定，避免模糊的「更好」 |
| 背景 | 讓沒參與的人也能理解來龍去脈 |
| 已知 | 只放可查證的事實，不放印象 |
| 假設 | 必須可逆，並寫出假設不成立時的替代做法 |
| 未知 | 影響方向、風險或不可逆成本的要問；否則寫打算怎麼查 |
| non-goals | 範圍外的事明確列出 |
| 里程碑 | 每個都要有可觀察的完成定義 |
| 工作分解 | 標出產出與負責角色，方便拆成任務簡報 |
| 依賴 | 寫出相依對象與影響 |
| 驗收條件 | 每一條都要對應一種驗證方法 |
| 風險與緩解 | 風險要搭配緩解，不要只列名稱 |
| 授權需求 | 把所有需要明確授權的動作集中列出 |
| 開頭四欄 | 標題後先用 blockquote 放讀者（含熟悉度）、一句話、現在要做、依據；四欄都要有實質內容。 |
