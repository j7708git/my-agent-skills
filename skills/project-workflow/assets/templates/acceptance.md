# 驗收（acceptance）

> 使用方式：把整份檔案複製到 private notes repo 的專案目錄，命名為
> `acceptance-<任務>.md`，逐項填寫。所有 `<...>` 都要換成實際內容。
> 「有檔案產出」不等於「已驗收」；沒測到的就寫「未測」。

## 骨架

```markdown
# 驗收：<任務名稱>

> **讀者**：<要複核這次驗收的人；寫明是否參與實作>
> **一句話**：<這次驗收的結論與最大缺口>
> **現在要做**：<要補測、修正或放行的動作>
> **依據**：<任務卡、實際指令輸出或 commit>

- 專案 ID：<project-id>
- 對應任務：<任務簡報或任務卡>
- 驗收時間：<YYYY-MM-DD>

## 驗收條件

- <條件一>
- <條件二>

## 驗證方法

- <條件一>：`<實際執行過的指令或操作>`
- <條件二>：<觀察方式>

## 實際輸出摘要

- <條件一>：<退出碼／關鍵輸出摘要>
- <條件二>：<觀察結果>

## 未測項目與原因

- <未測項目>：<為什麼未測>

## 結論

<通過／失敗／未完成；失敗或未完成要寫明缺口>

## 後續修正

- <需求誤解 → 修簡報；實作錯誤 → 修實作>

## 授權與同步狀態

- commit／push 是否已取得明確授權：<是／否／不適用>
- code repo 同步狀態：<狀態>
- notes repo 同步狀態：<狀態>
```

## 欄位填寫規則

| 欄位 | 填寫規則 |
| --- | --- |
| 對應任務 | 指向具體的任務簡報或任務卡，不要只寫專案名 |
| 驗收條件 | 一條一條列，對應計畫或簡報的驗收條件 |
| 驗證方法 | 寫實際執行過的指令或操作，不要寫「應該可以」 |
| 實際輸出摘要 | 附退出碼與關鍵輸出；秘密或個資要遮罩 |
| 未測項目與原因 | 沒測的就明說未測，不要美化 |
| 結論 | 只能選通過／失敗／未完成；未完成要寫缺口 |
| 後續修正 | 區分「修簡報」與「修實作」 |
| 授權與同步狀態 | 明確寫 commit／push 是否已授權，以及兩 repo 狀態 |
| 開頭四欄 | 標題後先用 blockquote 放讀者（含熟悉度）、一句話、現在要做、依據；四欄都要有實質內容。 |

## 注意

- 需要重跑才能確認的，重跑後再更新本檔。
- 不要把未測寫成通過，也不要用「看起來沒問題」代替結果。
- 同步狀態要與實際 `git status` 一致，兩個 repo 分開寫。
