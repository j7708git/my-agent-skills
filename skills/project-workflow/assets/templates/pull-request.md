# Pull Request（pull-request）

> 使用方式：在 ship 流程通過閘門後，把這份內容填進 PR body。所有 `<...>` 都要換成
> 實際內容；沒有 remote 或授權不明時只到 commit，不要開 PR。
> PR body 是公開內容：不得含 private notes 路徑、本機絕對路徑、機器名、內部帳號或
> private URL。先開 draft；驗收通過後才 `gh pr ready`。**合併由使用者決定。**

## 骨架

```markdown
# <變更標題>

> **分支**：<head branch> → **base**：<default branch>
> **任務**：<非敏感任務 ID 或一句話目標>
> **狀態**：<draft／ready for review>

## 目標

<這個 PR 要達成什麼、為什麼要做；一段可判定的說明>

## 變更摘要

- <檔案或子系統>：<改了什麼、為什麼>
- <檔案或子系統>：<改了什麼、為什麼>

## 驗證指令與結果

- `<實際執行過的指令>`：<exit code 與關鍵輸出摘要>
- `<實際執行過的指令>`：<exit code 與關鍵輸出摘要>
- 未測項目與原因：<沒有測到的部分，不要美化>

## 隱私掃描 exit code

- pre-commit：<exit code；0 通過、1 有發現、2 未掃完>
- pre-push：<exit code；只推非預設分支>
- 補充掃描：<指令與 exit code；沒有就寫「未執行」>

## 風險與回滾

- 風險：<這個變更可能影響什麼、誰會受影響>
- 回滾：<要怎麼回到變更前；是否只需 revert、是否有資料或設定要一起還原>

## 已知限制

- <尚未涵蓋的情境、已知缺口、後續任務>

## 驗收與合併

- 驗收方式：<tester／PM 的驗收紀錄或指令>
- 合併方式：<squash／依 repo 慣例；由使用者決定>
- base 狀態：<是否落後 default；若落後標「需 rebase」>
```

## 欄位填寫規則

| 欄位 | 填寫規則 |
| --- | --- |
| 變更標題 | 一句話講清楚改了什麼；公開 repo 的早期 draft 加 `WIP`，且只在閘門通過後才開 |
| 分支與 base | 寫實際的 head 與 base；base 是 repo 的預設分支，不寫死 `main` |
| 目標 | 可判定，避免「優化」「更好」這類空泛說法 |
| 變更摘要 | 依檔案或子系統分條，寫「改了什麼、為什麼」，不要只列檔名 |
| 驗證指令與結果 | 貼實際跑過的指令與 exit code；沒測到的明說「未測」 |
| 隱私掃描 exit code | 照抄 0／1／2 的語意；2 是未掃完，不能寫成通過 |
| 風險與回滾 | 風險要具體；回滾要能執行，不要只寫「有問題再處理」 |
| 已知限制 | 誠實列出未涵蓋的範圍，不要把半成品寫成完成 |
| 驗收與合併 | 合併由使用者決定；agent 不自動 merge、不 force、不改歷史 |
| 隱私 | 不寫 private notes 的具體檔案、本機絕對路徑、機器名、內部帳號或 private URL |
