# 專案總覽（overview）

> 使用方式：把整份檔案複製到 private notes repo 的專案目錄，命名為 `overview.md`，
> 再把所有 `<...>` placeholder 換成實際內容。不確定的欄位寫「未知」並註明查證方式，
> 不要留白、也不要猜。

## 骨架

```markdown
# 專案：<專案名稱>

> **讀者**：<第一次接觸這個專案的人；寫明需要的前置知識與熟悉程度>
> **一句話**：<這個專案要解決什麼問題、目前狀態>
> **現在要做**：<讀完後要做的決定或動作>
> **依據**：<需求來源、計畫或既有文件>

- 專案 ID：<project-id>
- 一句話說明：<這個專案要解決什麼問題>
- code-root：<公開程式碼 repo 的路徑，或研究類任務寫 N/A>
- notes-root：<private 工作紀錄 repo 的路徑>
- 目前階段：<規劃／原型／實作／驗收／維護>

## 目標

<可判定的目標，說明怎麼算完成>

## 範圍

<這次要做的事>

## non-goals

<這次明確不做的事>

## 關鍵里程碑

- <里程碑一>：<狀態>
- <里程碑二>：<狀態>

## 主要風險

- <風險>：<影響與緩解方式>

## 相關文件

- <相對路徑>：<用途>

## 更新紀錄

- <YYYY-MM-DD>：<變更摘要>
```

## 欄位填寫規則

| 欄位 | 填寫規則 |
| --- | --- |
| 專案 ID | lowercase kebab-case，與 code 子目錄名對齊 |
| 一句話說明 | 一句話講清楚痛點與價值，不要寫規格細節 |
| code-root | 實際路徑；研究類任務沒有程式碼就填 N/A |
| notes-root | 以工作區根為基準的路徑；不確定就寫未知 |
| 目前階段 | 只能選規劃／原型／實作／驗收／維護其中一個 |
| 目標 | 要能被驗證，避免「做得更好」這種無法判定的描述 |
| 範圍／non-goals | 兩者都要寫；範圍外的事放 non-goals，不要含糊 |
| 關鍵里程碑 | 每個里程碑都要有可觀察的狀態 |
| 主要風險 | 至少寫出影響與緩解方式，不要只列風險名稱 |
| 相關文件 | 用相對路徑，不寫個人絕對路徑 |
| 更新紀錄 | 每輪追加一筆，不要覆蓋舊紀錄 |
| 開頭四欄 | 標題後先用 blockquote 放讀者（含熟悉度）、一句話、現在要做、依據；四欄都要有實質內容。 |
