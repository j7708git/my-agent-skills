# diagram-guide

這是一份**圖解指引**：把「用圖說明流程與架構」從主觀選用變成可重複的判準。
它只管**怎麼畫、畫什麼、放在哪、怎麼驗**；什麼時候一定要有圖，由流程規則決定，
本 skill 不重複那一段。

- 預設用 **Mermaid**：純文字、寫在 Markdown 裡，OpenChamber 的 Markdown 檢視與
  GitHub 都能顯示，還能進版控、看得出改了什麼。
- 它是文字指引，不是繪圖工具：不下載、不安裝任何工具，也不自行 commit／push。
- 載入它**不等於授權**任何寫入或不可逆動作。

## 1. 先選圖型

| 要講的事 | 用什麼圖 | Mermaid 圖型 |
| --- | --- | --- |
| 步驟順序、閘門、失敗回圈 | 流程圖 | `flowchart TD` |
| 元件與資料流、誰呼叫誰 | 架構圖 | `flowchart LR`（分層用 subgraph） |
| 跨元件呼叫的時間順序 | 時序圖 | `sequenceDiagram` |
| 狀態與轉移（待處理→進行中→完成） | 狀態圖 | `stateDiagram-v2` |
| 排程與期限 | 甘特圖 | `gantt` |

其他 Mermaid 圖型（圓餅、類別、ER）照同樣原則用：**先問這張圖要回答哪一個問題**，
再選能最短回答它的那一種。同一份文件不要為了熱鬧，同時用三種圖型講同一件事。

## 2. 一張圖一件事

判準：**能用一句話說出這張圖在回答什麼問題**，才畫。

- 那句話裡出現「然後又」「順便也」→ 拆成兩張圖，或把細節留給文字。
- 一張圖的節點數以 5–9 個為宜；超過就先拆，不要靠縮小字級硬塞。
- 流程圖只畫**決策與交接**；單純的資料欄位、API 參數屬文字或表格。
- 同一張圖不要同時當流程圖與架構圖用：角色（誰做）與元件（什麼在跑）分開畫。

## 3. 節點要白話

節點是給人看的，不是給自己備忘的。**代號可以留，但要先講白話。**

| 反例 | 正例 |
| --- | --- |
| `T3` | 做登入畫面（T3） |
| `P2 gate` | 檢查通過才往下（P2） |
| `impl → tester` | 實作完成後交驗收 |
| `err path` | 驗收失敗：先分辨需求錯還是實作錯 |

規則：

- 節點文字用**動詞＋受詞**（「做登入畫面」），不要只寫名詞（「登入」）。
- 代號放括號當附註，不要當主詞；讀者不該為了看懂圖去翻任務卡。
- 判斷節點寫成**問句**（「驗收通過？」），兩條出邊標「通過」「失敗」。
- 一個節點只做一件事；「研究並規劃並派工」是三個節點。

## 4. 圖例門檻

- 節點**少於 5 個**：可省圖例，讀者一眼看得完。
- 節點**多於 5 個**：要圖例，說明形狀與線條的意思（實線＝必經、虛線＝選配、
  菱形＝判斷、粗框＝現在位置）。
- 圖例寫在圖的下方，用文字條列；不要只靠顏色，色盲與黑白列印會失真。

## 5. 標題要能自己解釋

標題寫「這張圖是什麼、包含什麼」，不要只寫「流程圖」。

- 反例：「流程圖」「架構圖」「示意圖」。
- 正例：「PM 標準工作流程（含選配的獨立複驗）」「匯入管線：從上傳到入庫」。
- 標題裡的專有名詞第一次出現時，在圖說用一句白話補上。

## 6. 什麼時候該改圖

只有**會改變讀者理解**的變更才需要改圖：

- **要改**：誰在什麼時候做什麼、有沒有閘門、失敗往哪走、元件之間多了或少了連線。
- **不用改**：純措辭、錯字、排版、同一件事換句話說。

改了流程、閘門、派工方式或角色分工，就在**同一個變更裡**更新對應的圖，
並把「圖與實作一致」列為驗收條件。只改文字卻讓圖過期，比沒有圖更誤導。

## 7. 圖的權威位置

**同一張圖只留一份原始碼**，而且跟講這件事的文件放在一起：

| 圖在講什麼 | 原始碼放哪 |
| --- | --- |
| 專案流程、里程碑、閘門 | 內部工作紀錄 repo 的專案計畫檔（`plan.md`） |
| 系統架構、資料流 | 程式碼 repo 的 docs 目錄 |
| 公開專案對外的流程 | 該 repo 的 README，直接內嵌 |

規則：

- 其他形式（手製 SVG、互動頁）是**產物**；與 Mermaid 並存時**以 Mermaid 為準**，
  並在產物的圖說註明「內容以相鄰 Mermaid 為準」。
- 不要把同一張圖的原始碼複製到第二個地方；要引用就寫「見某檔的某節」。
- 圖的原始碼跟著文件進版控；暫存截圖與匯出檔不進版控。

## 8. 驗收分級

分兩種，不要混用。

**正式驗收**（會影響「完成」判定）：

- 升級產物（互動頁、匯出的圖）交 `tester` 用瀏覽器實際開啟，確認渲染與內容。
- 任務卡寫明「圖與實作一致」，才把圖列入驗收條件；沒寫就不算。
- 驗收紀錄要寫「看了哪張圖、對到哪個流程」，不要只寫「圖沒問題」。

**日常習慣**（不算正式驗收）：

- 內嵌 Mermaid 由 PM（或文件作者）自己讀一次原始碼、開一次預覽，確認圍籬成對、
  節點沒被截斷。
- 渲染器不支援時，圖**照樣落檔**，回報改用純文字條列；不要因為看不到就刪圖。

## 9. 升級：什麼時候不只用 Mermaid

| 情境 | 做法 | 產物 |
| --- | --- | --- |
| 對外展示、圖很大、需要互動 | 載入 archify，把 Mermaid 的拓撲與語意改寫成互動頁 | 程式碼 repo 的 docs 目錄（`architecture.html`，進版控） |
| 只在對話裡快速溝通、不落檔 | 對話內 render | 不落檔，不當首選 |
| 需要版面、表格或多方案比較 | 對話內 render 或一般 Markdown 表格 | 依文件性質決定 |

archify **讀的是拓撲與語意，不是機械轉換**：內容不必重畫，樣式與版面由它重寫。
升級後仍以 Mermaid 那份為內容權威；互動頁是產物。

## 10. 常見失敗圖例（反例清單）

- **一圖多吃**：一張圖同時講流程、架構與時程，結果什麼都沒講清楚。
- **代號當主角**：滿圖 `T1`～`T9`，讀者要另一份對照表才看得懂。
- **沒有失敗路徑**：只畫順利的路，失敗與回圈全部消失。
- **閘門不見了**：把「先問使用者」畫成一般步驟，看起來像自動通過。
- **圖比文件新**：文件改了、圖沒改，讀者照著舊圖做。
- **圖比文件舊卻沒標**：保留舊圖時沒寫「以哪一份為準」。
- **圍籬沒閉合**：Mermaid 區塊少了結尾的三個反引號，整個檔案後半變成程式碼。
- **靠顏色說話**：只靠紅綠區分通過與失敗，黑白或色盲就讀不出來。

## 與其他流程的關係

- 什麼時候**一定**要有圖、圖要跟哪個變更一起改：由 PM 的圖解規則決定；
  本 skill 只給判準，不重複那一段。
- 交接文件要附圖時，權威位置與更新方式見第 7 節；對帳流程本身見 `handoff-refresh`。
- 需要獨立重跑、證明圖與實作一致時，見 `independent-rerun-verify`。
