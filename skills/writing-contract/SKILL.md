# writing-contract

這是一份**寫作契約**：把「文件該長什麼樣」拆成可判定的形式規則、可複製的模板，
以及四張自檢清單、一份重複句白名單與上游許可全文。它處理兩類文件，因為兩類讀者要的東西不同：

- **A 類：人看的敘述文件。** README、公開文件、任務卡、進度、計畫、驗收紀錄。
  讀者需要動機、脈絡與可掃讀的結構。
- **B 類：給 agent 看的指令檔。** `SKILL.md`、本集合 repo 的 AGENTS.md、agent 定義、
  派工簡報。讀者需要可執行指令、優先序，以及「什麼時候該停」。

上面出現的檔名是本集合 repo 的實例；獨立安裝 skill 時不是它的依賴。

## 什麼時候用

- 要新寫或大改一份 A 類文件，需要固定骨架與交付前自檢。
- 要新增或修改 B 類指令檔，需要確認第一段有優先序句、內容沒有混進通用寫作課。
- 要決定某條要求該寫成硬規則、寫作建議或反模式；先看規則的「為什麼」與「何時可刪」。
- 要維護填充詞、模糊詞或術語清單；只改 `assets/` 內對應的表。

## 兩類文件與規則

| 類別 | 對象 | 形式規則 | 主要輸入 |
| --- | --- | --- | --- |
| A 類 | 人看的敘述文件 | 機械：A1、A3、A5（400 行）、A9c；人工：A5 結構、A6、A7、A2r、A4r、A9r | `assets/fillers.md` 是唯一機械輸入；其餘是人工清單 |
| B 類 | 給 agent 看的指令檔 | 機械：B1；人工：B2、B3 | 無 |

- A 類的完整規則、理由與刪除條件在 `references/a-human-docs.md`。
- B 類的優先序句、插入位置與邊界在 `references/b-agent-docs.md`。
- 規則的衝突對與優先序（A6 > A5 > A1 > 其餘）也寫在 A 類 reference；
  衝突時要記下「哪條規則因為哪條而讓位」。

## 怎麼用

1. 先判斷文件類別。同一份文件不要同時套 A 類與 B 類規則。
2. A 類：用四欄 blockquote 開頭（讀者含熟悉度、一句話、現在要做、依據），
   再用專案既有的模板填內容。交付前跑一次 `references/a-human-docs.md` 的自檢清單。
3. B 類：第一段放優先序句，接著只寫三類內容——可執行指令、專案特有約定、
   禁止事項。不要重抄通用寫作規則。
4. 需要機械檢查時，使用集合 repo 提供的檢查器；它是維護工具，不是本 skill 的執行入口。
   檢查器的輸出全部是 warning，通過檢查只代表形式規則沒有命中。

## 與其他 skill 的邊界

- 本 skill 只管**寫出來的文件長什麼樣**；專案流程、派工、驗收與同步由
  `project-workflow` 負責。
- 本 skill 不是掃描器，不做隱私或秘密掃描；那由 `repo-privacy-audit` 負責。
- 本 skill 不會自動修復、不會改寫檔案、不會新增相依套件。
- 規則數不是越多越好：可同時滿足的規則增加時，遵循率會下降；因此只有能機械檢查
  或有明確證據的項目才寫成硬規則，其餘留在建議段。

## 不能宣稱什麼

- 通過形式檢查不等於文件好讀、正確或適合讀者。
- 本契約沒有做過 A/B 實驗，也沒有在任何 agent runtime 實測遵循率。
- 詞表只覆蓋列出的詞；沒有命中等於沒有檢查到，不等於文字沒有問題。
- 規則的證據多來自預印本、小樣本或單一語料，不能外推到所有專案與所有模型。
