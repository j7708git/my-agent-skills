# A 類規則：人看的敘述文件

> 本檔是規則本體。**只有 8 條機械檢查**；其餘規則是寫作建議與人工自檢。
> 沒被機械檢查到的項目，不代表不重要，只代表它不適合用低誤報的程式判定。

## 機械檢查（8 條）

| # | 規則 | 判定 |
| --- | --- | --- |
| 1 | A1 四欄存在 | 前 40 行內有四欄 blockquote |
| 2 | A1 四欄非空 | 不得為空、不得留 `<…>` 佔位符 |
| 3 | A1 現在要做 | 不得命中 `assets/fillers.md` |
| 4 | A1b 依據路徑 | 依據欄內反引號樣路徑必須存在；行號後綴會剝除 |
| 5 | A3 代號不單獨承載 | 整句只有「代號 ＋ 狀態詞」才報 |
| 6 | A5 單檔長度 | 單檔 > 400 行（只套 A 類；本專案自訂慣例，無文獻依據） |
| 7 | A9c commit SHA | 公開 A 類不得含 commit SHA；豁免 `owner/repo@<40 hex>` 形態的 action pin（含表格列）；裸的 40 位 hex 仍報 |
| 8 | B1 優先序句 | B 類第一段要有 B1 前綴；只比對句首前綴 |

**A1 沒有字數下限**：短值如「未知」「回報」可以；空值與 `<…>` 才算缺陷。
**A4r 對「一句話」欄豁免**：壓縮摘要不強制展開術語。
**A9c 的 SHA 範圍**：反引號、fenced code、URL 都查；action pin 豁免
`owner/repo@<40 hex>` 形態（含 Markdown 表格列），同一行其他裸 SHA 仍報。

## 僅人工自檢（明確沒有機械檢查）

| 規則 | 涵蓋範圍 | 已知繞過／限制 |
| --- | --- | --- |
| A5 單節條列 > 8、連續散文 > 3 段 | 單一 H2 的結構 | 跨行、嵌套與 diff 行號歸屬不可靠；8 條／3 段是本專案自訂慣例 |
| A6 章節下限 | H2 不得只剩標題與狀態詞 | 完整句、只有指令、明寫未知／待查都算合格；判斷需人看 |
| A7 模糊詞 | 正文散文；表格列、章節標題、引號內引用豁免 | 條件型 hedge 需同句有可觀察量或條件才報；表格與標題不查 |
| A2r 引用完整性 | 同一份詳細定義／指令只留一處 | **A2r 已無機械檢查（僅人工自檢）** |
| A4r 術語首次展開 | 正文散文中承重術語第一次出現給白話 | 縮寫不由機械檢查；簡體、插入空白、同義詞式註解都抓不到；註解 6–120 字是本專案自訂慣例 |
| A9r 不陳述未確認行為 | 不得陳述無法從程式碼或結果確認的行為 | 自動偵測不一致的 recall 只有 0.48，弱檢查只會製造噪音 |
| B2 只寫三類 | 指令／慣例／禁止事項，每條附「怎麼驗」 | 語意判斷，無機械檢查 |
| B3 不寫概觀 | 不寫專案概觀與逐檔說明；安全與授權例外保留 | 語意判斷，無機械檢查 |

**A9r 的界線：** 「不得陳述未經確認的行為」只做人工自檢；不把弱檢查寫成
「已由檢查器確保」。

**A 類 allowlist：** `docs/**/*.md`、`README.md`、`CONTRIBUTING.md`、`SECURITY.md`
與四個專案模板；`project-notes/` 不由本檢查器掃描。

## 優先序

**A6 > A5 > A1 > 其餘。** 衝突時以優先序靠前者為準，並在改版紀錄寫下
「哪條規則因為哪條而讓位」。

| 對 | 裁決 |
| --- | --- |
| A1 × A2r | 開頭摘要、結論段、TL;DR 不算重複定義 |
| A1 × A4r | 「一句話」欄豁免展開 |
| A1 × A5 | 四欄是 blockquote，不計入條列數 |
| A3 × A4r | 註解可以放在下一句；A3 只要求同句有述詞 |
| A4r × A5 | 縮短時不得刪掉白話註解 |
| A4r × A7 | 術語註解是定義上下文，不套用模糊詞黑名單 |
| A5 × A6 | 兩者都是觸發器；A6 優先，寧可補內容，不可直接刪 |
| B1 × B3 | 安全例外與「安全邊界以本檔為準」是同一件事的兩面 |
| B2 × B1 | B1 的回報要求就是 B2「怎麼驗」的一種 |

## 寫作建議

1. **結論先行。** 每段第一句說重點；不要用「隨著……的發展」開場。
2. **受眾分層。** 開頭寫明第一次接觸與已有脈絡的讀者各需要什麼。
3. **一段一任務。** 按讀者要完成的動作分段；真正並列的才用清單。
4. **變更程式碼時同批更新文件。** 不能同批改就標「待同步」與版本。
5. **關鍵事實放在動手當下會看到的位置。** 指令檔、任務卡與測試旁。
6. **同一概念只留一個叫法。** 改名時同步更新文件與術語表。
7. **不確定就寫「未知」。** 不要用猜測補滿欄位。

## 五種文件異味

| 異味 | 可指認的例子 |
| --- | --- |
| bloated（冗長離題） | 一段 80 字能講完的變更說明，被擴寫成含背景、動機與願景的三段 |
| fragmented（資訊散落） | 同一個安裝步驟分別寫在 README、維護指南與 skill 主文，三處版本不同 |
| tangled（敘述糾纏） | 一段同時講安裝、授權與回滾，讀者無法判斷哪一句屬於哪個動作 |
| excess structural info（樣板壓過內容） | 每個小節都套「目標／範圍／風險」三個標題，但內容只有一句話 |
| lazy（描述不足） | 章節只有「M3 完成」或「見程式碼」 |
