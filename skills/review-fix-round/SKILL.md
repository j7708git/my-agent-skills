# review-fix-round

這是一份**流程指引**，把「審查 → 裁決 → 修復 → 驗收 → 複審 → 紀錄」的修復輪
固定成可重複套用的協定，讓每一項 finding 的處置與理由都可追溯。

- 它是協定，不是審查方法本身：findings 的品質由審查者負責。
- 它是協定，不是掃描器，也不提供任何安全保證。
- 載入它**不等於授權**任何 commit、push 或不可逆動作。

## 什麼時候用

- 獨立審查（階段末、任務後、重要節點或外部審查）產出 findings 之後。
- 需要不只一輪「修復→複審」時：競態條件、發布前把關、契約變更。
- 需要留下「每一項 finding 被接受、駁回或延後的處置與理由」的可追溯紀錄時。

## 步驟

1. **審查**：findings 依嚴重度分級，每個 finding 要有**檔案與行號**，以及可操作的描述。
   - **必須修**：會造成錯誤、資料損毀、安全或契約破壞。
   - **建議修**：品質、可維護性、可讀性；不改也能運作。
   - **需驗證**：宣稱有問題但證據不足，要先查證再決定。
2. **裁決**：由決策者（PM 或指定的裁決者）逐項處置：**同意修／駁回／延後**，每項都要寫理由。
   即使沒有任何駁回，也要明寫「無 declined findings」，不要留空。
3. **修復**：以**限定範圍**的任務簡報或迷你卡派工，只修被裁決要修的項目。
   範圍外發現的問題**只回報**，不順手修。
4. **驗收**：以獨立重跑驗證修復結果，含對照組，證明斷言真的抓得到原本的 bug
   （做法見 `independent-rerun-verify`）。
5. **複審**：只回前輪的每一項（**Fixed** 或 **still open**），再加上新發現並分級。
   沒有新證據不要重開已結案項目。
6. **紀錄**：把逐項處置結果、殘餘風險（含理論邊界）、測試基準的變化，一次寫進驗收紀錄。

## 修復輪紀錄要有的欄位

| 欄位 | 內容 |
| --- | --- |
| 來源 | 本輪 findings 從哪次審查、哪個變更範圍來 |
| 分級 | 必須修／建議修／需驗證 |
| 裁決 | 同意修／駁回／延後，附理由 |
| 修復 | 改了什麼、對應哪個檔案或行為（限定範圍） |
| 驗收 | 獨立重跑的結果與對照組結果 |
| 複審 | 前輪每一項的 Fixed／still open |
| 殘餘 | 已知未解、理論邊界、明確不修的項目與理由 |

## 收斂與停止條件

- 複審只回前輪項與新發現；**理論邊界的殘餘不再開新輪**，改為記錄並交給決策者。
- 連續複審沒有新增的「必須修」項目時即可收斂。
- 每一輪都要有實質產出；只是重述同一批 findings 的輪次不算進展，應停下來檢討流程。
- 修復權與裁決權分開：修復者不自裁 self-approve，複審者不代替決策者決定駁回。

## 輸入與輸出

- 輸入：分級後的 findings（附檔案與行號）＋變更範圍或 commit 範圍。
- 輸出：逐項裁決紀錄、限定範圍的修復、複審結論（Fixed／still open／新發現）、殘餘清單。

## 明確不做的事

- 不自行駁回或自行延後 findings；駁回與延後由決策者具名決定並寫理由。
- 不擴大修復範圍，也不以「順便」名義改動裁決範圍外的檔案。
- 不為了讓測試變綠而刪除、跳過或弱化斷言，也不寫死測試輸入。
- 不用沒有證據的複審結論收尾；複審要有實際重跑或可核對的依據。
- 不改寫歷史、不強制推送、不改動其他任務的紀錄。

本指引由工作流健檢提案流程產生（2026-10-15）。
