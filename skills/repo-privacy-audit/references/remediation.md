# 處置手冊：發現疑似外洩秘密之後

這是**手冊**，不是自動修復流程。這個 skill 不會執行下面任何一個步驟；
每個步驟都要由你（維護者）明確決定與執行。

先講清楚三件事：

1. **清掉檔案裡的字串不等於止漏。** 真正止血是撤銷／輪替憑證。
2. **不能保證清乾淨。** 沒有任何流程能證明秘密不曾被複製過。
   誠實的結論是「風險已降低」，不是「已完全安全」。
3. **不可逆的動作需要人授權。** 歷史重寫、force push、可見度調整都要先取得
   明確同意，並留下紀錄。

## 處置順序（不要跳步）

| 順序 | 動作 | 是否可逆 | 誰決定 |
| --- | --- | --- | --- |
| 1 | 撤銷／輪替憑證 | 可重新簽發，但舊值永久失效 | 維護者立即執行 |
| 2 | 評估是否清理歷史 | 多半不可逆 | 需要明確授權 |
| 3 | 評估可見度與 fork | 會影響所有協作者 | 需要明確授權 |

---

## 第一步：撤銷／輪替憑證（永遠優先）

不論後面要不要清歷史，這一步都要先做。

### 1.1 判斷影響面

在動手前先回答，這決定你要多急：

- 這個 repo 是 private 還是 public？曾經公開過嗎？
- 是否已經推送到遠端？推送了多久？
- 有沒有人 fork 或複製過？
- CI 日誌、issue、聊天紀錄、PR 說明裡是否也出現過？
- 這組憑證在 CI secrets 或部署環境中是否可被多人讀取？

### 1.2 依類型撤銷

| 類型 | 撤銷位置 |
| --- | --- |
| GitHub token（PAT、fine-grained、OAuth、App token） | 帳號或 App 的憑證設定頁，全部撤銷後重新簽發最小權限版本 |
| 雲端存取金鑰 | 對應雲端的 IAM／存取金鑰頁；同時檢視稽核紀錄 |
| 資料庫密碼 | 資料庫的連線帳號頁；同時檢查是否有異常連線紀錄 |
| 套件發佈權杖（npm、PyPI 等） | 對應 registry 的權杖設定頁 |
| SSH 金鑰 | 把該公鑰從所有授權清單移除，再產生新金鑰對 |
| 密碼 | 走該系統的變更密碼流程，並檢查其他裝置是否仍被信任 |

### 1.3 建立替代品再撤銷舊的

順序有取捨，由你判斷：

- **懷疑已被利用**：立刻撤銷，接受服務中斷的風險。
- **沒有被利用的證據**：先建立替代憑證、驗證新憑證可用，再撤銷舊的，避免服務中斷。

無論哪一種，都要留下「舊值已於何時失效」的紀錄。

### 1.4 清理工作區與流程

- 把秘密移出受版控的檔案，改用環境變數或秘密管理工具。
- 提供不含真實值的範例檔（例如只有變數名稱的範例檔），並確認它已在忽略清單規則內。
- 更新 CI 的 secrets 與部署設定；不要把值寫進工作流程檔案。
- 移除工作目錄裡的暫存副本、備份檔與除錯用輸出。
- 重新執行掃描，確認工作目錄與 index 乾淨。

完成這一步之後，秘密在**歷史上**可能仍然存在。這就是第二步要處理的事。

---

## 第二步：評估是否需要清理歷史

**需要明確授權才能進行。** 理由：重寫歷史會改變所有 commit 的 SHA，
影響所有協作者、所有已開啟的分支與 PR，之後必須強制推送。

### 2.1 什麼情況才真的需要清理歷史

- 秘密確實被提交過，且不能只靠撤銷／輪替止血。
- 涉及個人資料、法務或合規要求。
- 政策要求 repo 不得保留任何憑證。

反過來說，如果秘密只在**未推送**的本地 commit，或撤銷輪替已完成且 repo 全程 private，
未必需要付出重寫的代價。這是判斷題，交給你決定。

### 2.2 授權前必須先講清楚的後果

- 所有 commit SHA 會變動；已合併的 PR 歷史會斷裂。
- 已 clone 的副本、fork、CI 快取、外部備份**不會**跟著更新。
- 需要所有協作者重新 clone 或重新對齊分支。
- GitHub 曾公開過的歷史，平台可能仍保留快取；這需要走 GitHub 官方的
  〈Removing sensitive data from a repository〉流程處理，無法靠重寫解決。
- 清理本身不能證明秘密從未被取用。

### 2.3 備份：先做，且要驗證

在動任何歷史之前：

```bash
# 1) 完整鏡像備份（包含所有 refs）
git clone --mirror . ../backup-<repo>.git

# 2) 標記備份對應的時間點，讓後續比對有依據
git -C ../backup-<repo>.git log --all --oneline | head
```

- 備份放在**受控位置**，不要放在同一台機器的公開路徑下。
- 記錄備份對應的 commit SHA 與時間。
- 備份本身含有秘密，請視為敏感資產並限制存取。

### 2.4 在隔離的 clone 演練，不要在原地試

```bash
# 3) 隔離副本：真正的重寫只發生在這裡
git clone --no-hardlinks ../backup-<repo>.git ../sandbox-<repo>
cd ../sandbox-<repo>
```

在這個副本裡：

1. 用歷史重寫工具（例如 `git filter-repo`）移除含秘密的檔案路徑或字串。
   舊的 `git filter-branch` 已被官方標示為不建議使用。
2. 逐一人工檢查被改動的 commit 數量是否合理；數量異常通常代表重寫範圍抓錯了。
3. 保留一份重寫前後的 commit 對照清單作為紀錄。

**請不要在原始 clone 上直接實驗。** 演練通過不代表可以省略授權步驟。

### 2.5 驗證演練結果

- 對副本重新執行掃描，確認目標秘密不再出現。
- 確認沒有誤刪無關的 commit 或檔案。
- 確認副本的 refs 與分支結構符合預期。

### 2.6 推送與授權

- 是否重寫、是否推送，由維護者逐案決定。
- 本手冊**不提供**一鍵 force push 指令，也不提供「自動修好」的腳本。
  這是刻意的：不可逆的動作要有人的判斷。
- 若你決定執行推送，注意區分「強制覆蓋遠端」與「帶租約的強制推送」兩種語意，
  並先確認遠端狀態符合你的預期。
- 把「誰授權、何時授權、範圍為何」寫進決策紀錄。

## 第三步：評估可見度與 fork

**需要明確授權。** 影響所有協作者與使用者。

- 評估是否需要調整 repo 可見度；調整前確認現有工作流程仍能運作。
- fork 的限制要知道：被 fork 出去的內容，**無法**靠改設定完全收回。
  已公開過的 fork 需要另外處理。
- 若需要平台層級的協助（例如清除已公開內容），走 GitHub 官方支援流程，
  並準備好 commit SHA、說明與處理時程。
- 不要為了「看起來比較乾淨」而調整可見度；那本身也可能是未經授權的變更。

---

## 第四步：個人資料專屬處理

個人資料的處置成本通常比憑證高，因為它難以「輪替」。

- commit 作者 email：考慮改用平台提供的匿名寄件地址設定
  （掃描器只辨識已知平台的匿名身分，不會因為字串含有 noreply 就放行），並評估清理既有 metadata 的成本
  （等同歷史重寫）。
- 移除或遮蔽文件、測試資料、日誌中的個人資料。
- 政策層面分三組設定，**不要混為一談**：
  - 電話型 email（local part 像電話號碼）預設已是 `high`，會擋住提交。
    若這是誤報（例如測試 fixture），用 `metadata.allowedEmails` 放行，
    不要為了滅燈把整組規則關掉。
  - 一般 author／committer email 預設 `low`。若公開 repo 不該出現這些地址，
    把 `metadata.emailSeverity` 明確調到 `medium` 或 `high`。
  - 台灣個資格式規則（身分證、信用卡號、手機號）預設**關閉**。
    確認需要後，把 `pii.enabled` 打開並評估誤報率。
    統一編號**不會**被比對（該規則未實作，政策寫了會被明確拒絕）。
- 個人本機路徑（`/home/<user>/`、`/Users/<user>/`）預設 `medium`，
  代表提交時可能帶出本機使用者名稱。清理方式通常是改寫路徑或排除該路徑樣式。
- 若涉及法規遵循，先確認適用的法域與申報義務，再決定處理順序。

---

## 第五步：收尾與驗證

1. 重新執行掃描，保存報告（遮罩後的內容），確認**退出碼**符合預期。
   注意：退出碼 `0` 只代表這次宣告的範圍內沒有 high 發現，不是「已完全乾淨」。
   若報告裡仍有 `coverage.limitations` 或 `errors`，那些位置這次沒有被掃到，
   要先處理才談得上驗證。
2. 把新憑證的取得與輪替方式寫進維護文件，讓下次不必重新摸索。
3. 檢視稽核紀錄，確認舊憑證確實已失效。
4. 若有權限，加入持續性的提醒（例如祕密掃描排程），並注意排程本身需要手動設定。
5. 在決策紀錄裡寫下：處置了什麼、還有哪些已知限制。

## 決策紀錄範本

| 欄位 | 內容 |
| --- | --- |
| 發現時間與來源 | 哪次掃描、哪個模式、哪個政策 |
| 秘密類型與位置 | 規則代號、路徑或 commit（**不要**記錄秘密本身） |
| 是否已推送遠端 | 是／否；推送時間 |
| 撤銷／輪替 | 何時、由誰、舊值是否已失效 |
| 歷史清理 | 是否進行；授權者與時間；備份位置；重寫範圍 |
| 可見度調整 | 是否進行；授權者與時間 |
| 殘餘風險 | 已知無法消除的部分（例如 fork、第三方快取） |
| 驗證方式 | 重跑掃描的結果與退出碼 |

## 明確不做的事

- 不提供自動改寫祕密、批次重寫歷史或一鍵 force push 的腳本。
- 不自動調整可見度、不自動封鎖帳號、不自動刪除 fork。
- 不把秘密原文寫進 issue、聊天紀錄、公開 gist 或任何範例檔。
- 不以「掃描過了」宣稱安全；沒有任何掃描能支持這個結論。
- 不宣稱「清乾淨了」。`references/checks.md` 列出的每一項不涵蓋都是真實的限制，
  誠實的結論是「已知風險已降低到這個程度」，不是「沒有風險」。
