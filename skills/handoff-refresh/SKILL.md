# handoff-refresh

這是一份**交接文件重生與對帳流程**，把「取最新事實 → 逐條比對宣稱 → 只改現況段 →
附證據 → 標快照時間 → 回報差異」固定成可重複套用的步驟，讓交接文件不會在同一天內
就變成三種互相矛盾的說法。

- 它是流程指引，不是產生器，也不是 Git 工具；不會自動 commit、push 或改寫歷史。
- 它**不改歷史段**：只重生「現況／下一步」，已收案的敘述與流水帳一律不動。
- 它不保證文件一定正確；能保證的是「每一條現況宣稱都指得出證據位置」。
- 載入它**不等於授權**任何寫入、提交或推送；寫入範圍要先取得明確同意。

## 什麼時候用

- session 收尾、要交接給新 session／新 agent、或跨機接手之前。
- 里程碑完成、PR 合併、發版之後，需要更新「現況／下一步」。
- 健檢或接手時發現交接檔、總覽、計畫三者與進度紀錄說法不一致（同一份檔案自相矛盾、
  或同一件事在三份文件裡有三種狀態）。

## 名詞與角色

| 名詞 | 意義 |
| --- | --- |
| 權威來源 | 進度紀錄（`progress.md`）的最新段，加上兩個 repo 的 Git 事實（HEAD、tag、工作樹） |
| 交接檔 | `HANDOFF.md`：只放「兩 repo HEAD＋版本線＋接著做」與接手必須知道的速查 |
| 總覽 | `overview.md`：入口頁；「目前狀態」只指向權威來源，不重複寫分支與 commit |
| 計畫 | `plan.md`：任務表只記「完成／已合併」與收案註記，細節指向權威來源 |

規則：**同一件事只寫一處。** 狀態寫在權威來源；三份文件只保留指標與最小快照。
重複寫第二次，就是下一次漂移的起點。

## 前置：先確認三件事

1. **權威來源在哪**：進度紀錄的路徑、以及它「最新段」是哪一段（見步驟 1 的判定規則）。
2. **要更新哪幾份文件**：只處理存在的檔案；缺哪一份就在回報裡寫明，不要順手新建。
3. **寫入範圍與授權**：哪些段落可改（現況／下一步）、哪些一律不動（歷史、流水帳、
   已收案敘述、他人未提交的變更）。沒有明確同意就不要動。

## 步驟

1. **取最新事實**
   - 讀進度紀錄的**最新一段**，不是最後一段：依「日期＋時間」排序判斷，檔案尾端不一定是
     最新（同日可能有多段，且可能不是依時間追加）。找不到時間戳時，以段落標題的日期為準，
     並在回報裡標明判斷依據。
   - 兩個 repo 各取：`git rev-parse --short HEAD`、`git status --short`、`git log --oneline -n`、
     `git describe --tags --abbrev=0`（或等價的 tag 查詢）。分支清單用唯讀查詢，不要切換分支。
   - 版本線以**已推送的 tag** 為準，逐一確認每個 tag 指向哪個 commit；**不要假設
     「主線 HEAD 就是已發佈版本」**——tag 之後的 commit 屬於下一個版本。
   - 任務與驗收索引只讀檔名（`tasks` 目錄、`acceptance` 目錄），不逐檔讀完。
2. **逐條比對三份文件的宣稱**
   - 把三份文件裡每一條「版本／HEAD／分支狀態／完成與否／下一步」抄成清單，**一條一行**。
   - 每條標記：相符／過時／矛盾。矛盾項優先處理，過時項次之。
   - 特別檢查三種常見殘句：同一份檔案開頭與標題互相打臉、分支狀態寫了兩次、
     下一步仍在要求「合併／commit」已完成的事。
3. **只改「現況／下一步」段**
   - 交接檔：標題與狀態段只留「兩 repo HEAD＋版本線＋接著做」；其餘交付內容標成
     「某日事實記錄」，不再逐日更新。
   - 總覽：把「目前狀態」收成**一段指向權威來源的說明**，刪掉重複的分支與 commit 狀態。
   - 計畫：任務表只改狀態欄與收案註記，寫「已合併／已 commit」，細節指向權威來源段落。
   - 歷史段、流水帳、已收案敘述、他人的未提交變更：**不動**。需要修正的，只在回報裡列為
     「建議另案處理」。
4. **每條宣稱附證據位置**
   - 現況段裡的每個事實，都要能指到「檔案＋行號」或「commit／tag」。指不到證據的句子，
     寧可刪掉也不要留著。
   - 引用的是本機未推送的 commit 時，明確寫「僅本機可見」。
5. **標快照時間與優先序**
   - 在現況段開頭寫快照日期，並固定一句「若早於權威來源的最後更新，以權威來源為準」。
   - 快照時間要跟證據一致：文件寫 10-21，就不能引用 10-22 才產生的事實。
6. **回報差異與未解項**
   - 列出：改了哪些檔案（各一句）、哪些宣稱被判過時或矛盾（附原位置）、哪些需要
     PM／使用者決定、哪些沒解（含原因）。
   - 明說是否提交：預設**不** `git add`／`commit`／`push`，由持有 index 權限的人決定。

## 逐條比對表（建議欄位）

| 宣稱 | 出處（檔案＋行） | 事實（含證據） | 判定 | 處置 |
| --- | --- | --- | --- | --- |
| 例：某 PR 尚未合併 | 交接檔某行 | merge commit 已在主線，`git log` 可查 | 過時 | 改寫為已合併，指向權威來源 |

判定只用三種：相符／過時／矛盾。「存疑」單獨列在回報，不要混進文件。

## 輸入與輸出

- **輸入**：進度紀錄（最新段）、兩個 repo 的 Git 狀態與 log、任務與驗收的檔名索引、
  三份文件現有的現況段、可寫入範圍。
- **輸出**：重生後的交接檔現況段、總覽的目前狀態、計畫的任務表狀態、
  「宣稱↔事實」差異清單（含證據位置）、未解項清單。

## 失敗與例外

- **權威來源與 Git 互相矛盾**（進度紀錄說已合併，`git log` 查不到）：**停下來回報**，
  不要自行選一個當事實，也不要把矛盾寫成「大致一致」。
- **權威來源本身過時**（例如「下一步」節停在更早的日期）：照用，但在快照段標明
  「該節為某日快照」，並把刷新它列為未解項，不要假裝已同步。
- **工作樹有未提交變更**：HEAD 描述要寫明「含未提交變更」，不要把未提交的內容說成已入庫。
- **文件缺漏或格式不合**（沒有任務表狀態欄、標題層級不一致）：只回報，不重排格式。

## 明確不做的事

- 不改歷史段、不刪流水帳、不合併章節、不重排文件格式。
- 不自行 commit、push、改寫歷史、調整可見度，也不碰他人未提交的變更。
- 不把「掃描通過」「測試全綠」之類的舊宣稱順手升級成新結論；沒有新證據就維持原樣、
  標為未驗。
- 不在文件裡寫入憑證、真名、私人 email、帳號 ID 或本機絕對路徑。

## 與其他流程的關係

- 通用流程、兩個 repo 的分工與授權邊界：見 `project-workflow` skill；本 skill 只處理
  交接文件的對帳與重生，不重複它的規劃、派工與同步步驟。
- 任務卡與「展示副本」（計畫面板裡的卡片）的同步：屬另一個主題（提案
  `task-card-display-sync`）；本 skill 不動卡片與副本，只在計畫的任務表改狀態欄。
- 發版本身的整備順序：見 `release-prep` skill；本 skill 只把發版結果寫回現況段。
