# native-crash-triage

這是一份**證據處理流程**，把「崩潰報告 → 符號還原 → 跨案比對 → 機制驗證 →
分層筆記」固定成可重複套用的步驟，讓每次歸因都能被別人照著複核。

- 它是流程指引，不是除錯器，也不自動解析或下載任何符號檔。
- 它不保證歸因正確；結論的強度取決於證據分層是否誠實（事實／推論／未知分開寫）。
- 載入它**不等於授權**任何寫入、提交、推送或修改既有筆記。

## 什麼時候用

- 使用者回報原生閃退（macOS `.ips`、診斷匯出、Apple 崩潰全文、Breakpad 或
  minidump 的符號化輸出）。
- 需要與舊崩潰案比對歸因（同一個症狀是不是同一個機制）。
- 需要驗證某個修法是否真的移除了致命配置點，而不是只讓症狀消失。
- 需要把一次 triage 的推論鏈寫成別人可以複核的紀錄時。

## 前置：邊界與授權

1. 確認本次授權範圍：只讀分析、寫筆記、改程式碼、跑實驗、提交，是**不同**的授權；
   沒被授權的動作不要順手做。
2. 確認手上有的材料：崩潰報告、發生時的版本、使用者描述的觸發情境、對應版本的
   官方符號檔。缺哪一項就在紀錄裡標「未知」，不要用猜的補。
3. 崩潰報告是使用者資料：只放在版控之外的暫存位置（例如已被忽略的 `.tmp`），
   不要貼進公開 repo，也不要放進會被提交的筆記。

## 步驟

1. **收件與去識別**
   - 保存原始報告（不要只留截圖），計算雜湊或記下檔名與收到日期，作為本案案號。
   - 去識別：使用者名稱、主機名、家目錄路徑、專案資料夾名、email、機器序號、
     組織名稱全部換成 placeholder；只保留分析必要的欄位。
   - 確認報告與暫存位置都在版控之外；若專案沒有忽略規則，補上忽略規則屬於寫入，
     先取得授權再動。
2. **讀 metadata 與 body，抽出崩潰簽名**
   - 逐欄記錄：exception type、termination reason、signal、faulting thread、
     PC 位址與 PC bytes、關鍵 frame、binary image 的 UUID 與架構、OS 與 app 版本、
     是否為記憶體壓力終止（jetsam）或 watchdog。
   - 同一案的 `.ips`、診斷 JSON 與使用者貼上的全文，欄位名可能不同；**以 body 的
     frames 為準**，其他格式只用來交叉核對。
   - 把簽名寫成一張表：一欄是值，一欄是「這個值從哪個欄位讀來」。沒有來源的值不算證據。
3. **符號還原（逐格）**
   - 用 binary image 的 UUID 取**同一個 build** 的官方符號檔與符號表
     （dSYM、Breakpad symbol 或平台對應格式）。鄰近版本的符號不能用來補洞。
   - 對每個 frame 記錄：原始位址、所屬 module、還原後的函式、offset、是否內聯。
   - **回址界線**：return address 要用 `addr−1` 查表，因為堆疊上的回址指向呼叫敘述的
     下一行。直接查原值常會落在下一個函式的第一個指令。
   - 尾端呼叫（tail call）會讓「函式結尾」等於「下一個函式起點」；遇到這種情形，
     要把兩個候選都寫出來並說明判斷依據，不要只挑一個當定論。
   - 內聯展開的 frame 要標示出來，它不代表獨立的呼叫層。
   - **trap 時的暫存器值不可當作尺寸證據**：常數與實際長度可能同值。要改用鄰近的
     記憶體操作、allocation 紀錄或第 5 步的實驗量測。
   - 符號 UUID 與報告不符、或查不到官方符號時，**停在這裡回報**，不要用位址猜函式名。
4. **與舊案逐格比對**
   - 比對維度至少包含：崩潰簽名、配置點所在的 stack 段與其位址、binary UUID、
     thread 數與發生時序、faulting frame 序列、終止原因。
   - 每個維度只寫三種結果：**相同／不同／無法比較**，並附依據（哪個欄位、哪次實驗）。
   - 差異本身不是結論；寫出「這個差異對歸因的影響是什麼」，或明說目前無法判定。
   - 舊案資料不可得時，把該維度標成「無法比較」，不要用印象補。
5. **機制驗證（涉及修法時必做）**
   - 設計**單變數對照實驗**：只改一個變因，兩組跑相同輸入與相同環境。
   - 量測數字（差值、倍率、樣本數），不要只寫「變快」「不再崩潰」。
   - 對照組要能證明量測抓得到原本的現象；抓不到就代表實驗設計無效，先修實驗。
   - 為了讀數字而暫時打開的儀器（log、計數器、debug build）用完要還原，
     並在紀錄裡寫明開過什麼、已還原。
6. **分層寫筆記**
   - 固定五層，缺一層就明說「本輪沒有」：
     **事實**（可直接從報告或實驗讀出，附來源欄位）、**推論**（附推理鏈與前提）、
     **未知**（還缺什麼證據、怎麼取得）、**已知坑**（這次踩到、下次要避免）、
     **來源**（報告、符號檔、版本、查詢日期）。
   - 推論不得寫成事實；「未找到」不等於「不存在」。
   - 筆記放在團隊約定的內部工作紀錄位置；不要寫死只有某台機器才有的路徑。
7. **回報與舊筆記的出入**
   - 若結論與既有筆記不同，列一張清單：哪一份筆記、哪一段、何處有出入、依據為何。
   - **不要自行修改舊筆記**；勘誤或補充由筆記的擁有者決定並具名 append，
     附上日期與依據。
8. **隱私複核**
   - 掃描本次產出：不得出現使用者名稱、主機名、資料夾名、絕對路徑、email、憑證。
   - 需要引用報告片段時，只留去識別後、且對分析必要的最小片段。

## 本次 triage 紀錄要有的欄位

| 欄位 | 內容 |
| --- | --- |
| 案號 | 收件日期＋去識別後的報告識別（雜湊或檔名） |
| 版本與環境 | app 版本、OS 版本、硬體架構、binary UUID |
| 簽名 | exception、faulting thread、PC、關鍵 frame、終止原因 |
| 還原 | 每個 frame 的函式與 offset；回址是否已取 `addr−1` |
| 比對 | 與舊案的各維度結果（相同／不同／無法比較）與依據 |
| 機制 | 對照實驗的設計、量測數字、對照組結果 |
| 分層 | 事實／推論／未知／已知坑／來源 |
| 出入 | 與舊筆記的差異清單（沒有就寫「無」） |
| 隱私 | 已去識別的項目清單 |

## 停止條件（卡住就回報，不要硬推）

- 報告缺少 faulting thread 的 frames，或 frames 被截斷。
- binary UUID 與手上符號不符，且拿不到正確 build 的官方符號。
- 實驗無法隔離單一變因（同時改了多個條件），或對照組抓不到原現象。
- 歸因需要舊案資料，但舊案不可得。
- 需要超出授權範圍的動作（改程式碼、開 instrumentation、提交）。

遇到以上任一項，把已知與未知寫清楚後回報，不要為了給出結論而降低證據標準。

## 輸入與輸出

- 輸入：崩潰報告檔（含 body）、對應版本的官方符號與符號表、舊案紀錄（可選）、
  使用者描述的觸發情境。
- 輸出：分層的 triage 紀錄、逐格還原表、跨案比對表、可複核的實驗數字、
  與舊筆記的出入清單。

## 明確不做的事

- 不用未符號化的位址猜函式名，也不用鄰近版本的符號補洞。
- 不把 trap 暫存器值當成尺寸或長度證據。
- 不自行修改舊筆記；勘誤由擁有者決定。
- 不把崩潰報告、使用者資料或去識別前的片段放進公開 repo。
- 不在缺少證據時寫出確定語氣；不為了敘事完整而補不存在的推論。
- 不順手修範圍外的程式碼；發現的問題只回報。
